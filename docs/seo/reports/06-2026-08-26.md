## 3. What the site publishes that the product does not support

### 3.1 "84 Languages", unqualified — the one that matters

`src/components/home/SocialProof.astro` renders it as a flat stat. `src/pages/llms.txt.ts` opens
with *"voice-to-voice across 84 languages"*. `/{lang}/business/` says transcripts are *"translatable
into 84 languages"*.

Verified against the live catalogue (`GET api.voxtranslate.app/api/languages` and `/api/engines`,
checked 2026-08-26, matching the committed `src/data/engines.json`):

| Tier | Engine | Languages | Rate / min / target language |
|---|---|---|---|
| Standard | Qwen LiveTranslate | **29** | $0.0045 |
| Enhanced | Cartesia | **61** | $0.0666 |
| Premium | Gemini 3.5 Live | **84** | $0.06845 |

84 is the size of the **catalogue** and the reach of **one** tier. `server/src/engine/langmap.rs:9-13`
explains why Standard is 29 and not 60: Qwen reaches 60 targets but only 29 with audio, and *"offering
a text-only language on a speech-to-speech tier hands the user subtitles and silence."* That is
exactly the right instinct, and the homepage undoes it.

This was already known internally. `docs/marketing/directory-listings.md:17-18`: *"Only Premium
covers 84. The homepage headline currently overstates this."* Dated 2026-08-05.

### 3.2 Currency

Everything the server bills is **USD**. `server/src/engine/metadata.rs:53` documents
`cost_per_minute` as USD; `CreditPackage` carries `price_usd` / `credits_usd`
(`server/src/config.rs:1103-1110`). The site is consistent with this since `feature/usd-plan-prices`.
Any external brief quoting a euro per-minute rate is wrong.

## 5. Not verified — must not be published

stated three times independently: `docs/marketing/directory-listings.md:16` (*"No latency numbers.
None has been measured on the shipped build. Do not add one."*), the extension's

**"Local recording is free."** No local-recording code path was found. Recordings go to a

local-recording path has to exist and be pointed at.

**Business $49 / Enterprise $199.** `docs/marketing/directory-listings.md:20-22` flags a currency
mismatch between the site and Stripe. The locale files now say `$`, and `feature/usd-plan-prices`
appears to have addressed it, but the Stripe Price objects themselves carry the authoritative
currency and were not reachable from here. **Left untouched.** Someone with Stripe access should
confirm and close the note in that file.

**Stale comment, flagged not fixed.** `server/src/webinar/stt.rs:20` says *"translated TTS audio is
out of scope here — subtitles only."* The Enhanced webinar TTS path shipped after it was written.
The comment misleads anyone reading webinar code; correcting it belongs to a server change, not to

## 6. Infrastructure findings

**GA4 has never recorded anything in production.** `src/lib/site.ts` reads `GA_ID` from
`PUBLIC_GA_ID`; `.github/workflows/deploy.yml` passes `POCKETBASE_URL` and `PUBLIC_FB_PIXEL_ID` and
**not** `PUBLIC_GA_ID`. Empty ⇒ `gtag.js` never loads ⇒ every `track()` call on the site is a no-op.
The consent architecture around it is correct and is not being changed: `ConsentBanner.astro` loads
trackers only after an explicit accept, and reloads the page on reject to drop anything already
loaded. Needs a GA4 Measurement ID from the owner; the wiring is added regardless so it works the
day one exists.

**No staging.** `deploy.yml` fires only on push to `main`. The staging *mode* is fully implemented
— `functions/_middleware.ts` step 0 short-circuits into Basic Auth + `X-Robots-Tag: noindex`
whenever `STAGING_BASIC_AUTH` is set, deliberately **before** the `*.pages.dev` → apex 301 that
would otherwise make a preview host unreachable. Only the deploy job and the environment variable
are missing.

**`SOCIAL` in `src/lib/site.ts`** holds placeholder X and GitHub handles and is imported by nothing.

**`/contact` 404s** on both the apex and the app host, while `voxtranslate-chrome-extension/PRIVACY.md:113`
and `docs/store/data-disclosure.md` both print it as the support URL. A user following the Web Store
privacy notice hits a dead page.

## 10. The finding that was not in the brief

**The blog was publishing a latency number the server source says is wrong.**

`src/data/fallback-posts.ts` and `src/data/post-translations.json` carried *"roughly
sub-250-millisecond responsiveness"* for the Enhanced tier across three articles, in all
five locales; `new-posts.json` carried *"sub-250ms latency"* twice more. **Nineteen
occurrences.** Plus superlatives leaning on the same claim — "the low-latency path", "the
lowest-latency back-and-forth", "der Pfad mit der geringsten Latenz", "latenza minima",
"mínima latencia", "latence minimale".

`server/src/engine/cartesia.rs:44-46` addresses this figure directly:

> No latency figure here, deliberately. It was wrong (Enhanced is not the fastest tier),
> and a number in shipped copy becomes a promise the product has to keep on every network.

**Why the existing gate did not catch it.** `src/lib/measurements.ts` fails the build on an
unmeasured number — but it guards the SEO tree, where numbers come from measurement files.
The blog is `src/data/*.json` prose fetched from PocketBase or bundled as a fallback, and
nothing inspects it. The rule was enforced exactly where it had been written down and
nowhere else.

All nineteen are gone. Where a paragraph existed only to make the speed argument, it now
says plainly that no latency figure is published and why — matching `/{lang}/chrome/` and
`/latency/`. The Features card titled "Low-latency & private" became "Peer-to-peer &
private" in five locales; its own body was always about WebRTC and media never touching our
servers, and the title was claiming something the body did not support.

**Worth someone's attention:** the same class of claim could re-enter through PocketBase,
which is not covered by any gate. A content-lint step over `src/data/*` and the fetched
posts would close it. Not done here — it is a task, not a line.

## 11. Second finding: the SEO tree had no heading scale

Fifty-plus pages rendered h1, h2, h3 and body text at identical size. Tailwind's preflight
resets headings to `font-size: inherit`; `global.css` sets family, weight and colour for
h1–h4 but no size, because home-page components set their own. Pages built from a bare
`<slot/>` had nothing to restore it.

The document outline was always correct — one h1, properly nested h2s — which is why no
automated check flagged it, and why a screen reader was unaffected. A sighted reader had to
infer structure from bold text. Fixed once in `SeoLayout`, scoped to `.seo-body`.

## 14. What CI caught that a local pass did not

Worth recording, because it is an argument for the gate rather than a footnote.

The first `verify:schemas` + build + local Lighthouse pass was green on every page written
in this task. CI then failed `/live-translation/` at **SEO 0.93** against the 0.95 bar,
identically across all three runs. The audit was **`tap-targets`**: its navigational link
lists measured 21px tall with 6px between them — under WCAG 2.5.8's 24px minimum and well
under the 48px Google asks for.

That was always true of the persona list. Adding the platform and guides lists to the same
page is what turned a latent problem into a failing audit, and the local pass missed it
because it only covered the pages that were new, not the page they were added to.

Pulling the CI artifact then surfaced two more, on the blog index, both pre-existing:

- **`heading-order`** — `PostCard` hardcoded `h3`, so the index ran h1 → h3 with nothing
  between. It could not simply become `h2`, because `BlogLayout` renders the same card
  under a "Related articles" `h2` where `h3` is right. The level is a prop now.
- **`label-content-name-mismatch`** — every card link carried `aria-label={post.title}`
  while its visible content is tags + title + excerpt + date, so the accessible name was
  *narrower* than the visible label. That is the failure a speech-control user hits when
  they say what they can see and nothing happens. The link already contained the title;
  the aria-label was overriding a correct name with a worse one.

All three fixed. Every page in the CI matrix now scores accessibility **1.0** and SEO
**1.0**, except `/latency/` and `/languages/` at SEO 0.69 on `is-crawlable` — their
deliberate `noindex`, already excluded in `lighthouserc.json`.

`/en/` measures **0.92** mobile performance, against the 0.84 recorded in
`docs/seo/reports/00-2026-08-06.md`. It is still a WARN rather than an ERROR and this task
did not set out to fix it, but it did not make it worse.
